## Engine route and declared interventions

The stock console helper `Console.mta(area)` invokes `GemRB.MoveToArea`. The
export moves selected PCs to the destination map but preserves their old
coordinates. The external host therefore:

1. Records all four original party identities and the zero-gold AR0602 state.
   `GameSelectPC(0,1)` is the documented select-all route. Actual selected flags
   and actor IDs are recorded and checked before moving.
2. Calls `MoveToArea('AR0704')` once. It queues a parsed
   `JumpToPoint([x,y])` through `ExecuteString(action,slot)` for each exact party
   slot, using (690,550), (730,550), (690,590), (730,590), then restores leader
   walking selection. These are debug setup commands, not ordinary player travel.
3. Proves actual queued action IDs against the frozen action.ids JumpToPoint
   entry. It waits for automatic `Interface`/`GameControl.ChangeMap`, all four
   actors in AR0704, four idle samples, empty action queues and adjusted positions
   within 96 pixels of their declared destinations. Entry is never completion.
4. After an ordinary zero-gold affordability case and closing the store, requires
   gold exactly zero and invokes the existing exported
   `GameSetPartyGold(100,1)` once. Its nonzero second argument calls `Game::AddGold`,
   so the separately captured result must be exactly 0→100 with no other world
   mutation. It does not change character inventory, XP, spells, globals or STO
   prices. This isolated grant is not added to the original parent or baseline.

Source authority is GUIScript.cpp's documented GameSelectPC, MoveToArea,
ExecuteString and GameSetPartyGold exports; GameScript.cpp queues generated
actions; Actions.cpp's JumpToPoint calls `SetPosition(point,true)`; Interface.cpp
switches to the first selected actor's map. Their actual source bytes, along
with Map/GUI/dialogue/importer code, are explicitly frozen. No GAM/CRE/ARE binary
patch or direct actor-position setter is used by the external tool.
