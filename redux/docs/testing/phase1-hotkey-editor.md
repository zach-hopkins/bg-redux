## Existing routing and the correction

`GUIOPT.OpenHotkeyOptionsWindow` was a TODO behind an active BG2EE gameplay-options button. The preserved PST keyboard screen is also a static placeholder; opening it would not implement an editor. `KeyMap::InitializeKeyMap` reads action names and one-character aliases from the original game/resource INI plus `keymap.2da`. Normal `GameControl::OnKeyPress` resolves unmodified keys through KeyMap after its fixed-key handling; modifier/debug and script fallback routing is separate. `MenuWindow.InitOptionButton` additionally creates global **application** button shortcuts from action names. Those cached registrations must change together with KeyMap; changing only the resolver leaves old keys active.

The new editor uses the current game NORMAL/STONESML roles and native modal/controls over existing GUI primitives. It shows supported loaded action bindings, lets a player select an action, type one plain key, Assign, Clear, explicitly Replace a conflicting binding, stage Defaults, Apply or Cancel. It uses real mapping/persistence operations rather than opening a dummy window to satisfy a transition check. Pending errors/conflicts are visible. Apply validates and saves; Cancel/Escape closes without changing the live map or persistence. Defaults restore the original game/resource binding values captured before profile overrides, and stay staged until Apply.

The present scope is existing supported, loaded, unmodified ASCII action bindings. Letters and ordinary unmodified punctuation are editable; fixed digits/party selection, pause, arrows, function keys, console and modifier/debug routes remain under their current routing. Unsupported/default-no-op actions and a key held by a non-editable route cannot be stolen. This does not claim every EE action/combination or international keyboard layout is implemented. A cleared action remains in the catalog so it can be assigned again after restart.

## Backend and consistency

`GetKeyBindings()` returns the native action/current/default/group catalog. `SetKeyBindings(mapping, dry_run)` accepts a complete set of known supported names and empty/single key strings. Native validation rejects unsupported/fixed keys, unknown/missing actions, duplicate nonempty keys and conflicts with non-editable aliases. It builds replacement maps before swapping them in, so key swaps and clears do not partially mutate live routing on validation failure. Neither API executes an action or attaches an OS shortcut.

`KeyBindingEditor.Draft` keeps edits separate from the live map. It rejects a stale editor snapshot, performs native dry-run validation, atomically writes a unique temporary file and replaces only `<SavePath>/gemrb-keymap.ini`, then applies the live map and refreshes named menu registrations. File-write failure does not apply live changes; live apply/rebind failure attempts to restore both previous routing and previous profile bytes, exposing any failure rather than saying saved. No original game `keymap.ini`, save GAM/SAV, global system preference or engine config is rewritten by this operation.

KeyMap initializes the original game mapping first, then validates/loads the profile override as a whole. Malformed/duplicate/unknown profile rows retain the original mapping and emit a warning. Empty profile values clear bindings. The profile is associated with the engine's selected SavePath; independent private LAB profiles therefore remain separate. Native library mode has no keymap and rejects these APIs explicitly.

`MenuWindow` tracks only scripting identities of controls it initialized with named shortcuts. Rebinding first clears all old registered keys, then assigns characters while retaining each button's existing action callback. It does not recreate windows, retain actors/windows across loads or replace a custom mouse callback through the name-based SetHotKey overload. Deleted windows are skipped; newly created menu controls obtain the current map normally. The normal modal event/focus policy remains responsible for keeping gameplay/menu keys from firing while typing in the editor; this requires native interaction validation.

## Native callback argument defect

The first native menu run `20261022T010029Z-menu-run-bf0932e2/1024x768` exposed production Stats failures: native `OnPress` supplied a GButton into the first positional `section=index` / `step=delta` lambda argument. Category selection therefore passed a button to SetVar and page navigation attempted int+GButton. `PythonComplexCallback::GetArgs` in `PythonCallbacks.h` checks `co_argcount` and supplies the control when nonzero; default-valued arguments are still positional parameters. The earlier test double invoked these callbacks without the real control argument and missed the error.

Stats category/page and hotkey row/page closures now reserve an explicit ignored first control argument, preserving their captured integer. The same inspection found that binding the optional-parameter `Assign(replace=False)` directly let the native GButton become a truthy replacement flag. Assign's registered callback now explicitly ignores its control and calls Assign without replacement; explicit Replace remains the only conflict replacement route. Focused tests now supply actual control doubles to these callbacks, including conflict refusal and multi-page row navigation. **17 character-sheet tests and 14 hotkey tests pass.** No callback bridge or engine source changed. Fresh native callbacks/dispatch remain required; the failing native run is preserved.
