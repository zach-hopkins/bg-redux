## Similar dialogue pixels can have different causes

**EE portrait overflow: [#2271](https://github.com/gemrb/gemrb/issues/2271)**, closed 2025-01-15, updated 2025-01-16, six comments. The mixed installation/chargen report explicitly includes dialogue text exceeding its window. The [maintainer's diagnosis](https://github.com/gemrb/gemrb/issues/2271#issuecomment-2593743857) attributes that symptom to oversized EE portraits and points portrait sizes/user-directory discovery to #164; it separately reports fixes for chargen controls/stat placement. This gives a concrete portrait-size/clipping lead, not evidence that stale removed choices share that cause. Our approved modern layout still needs portrait-aware text bounds and ordinary long-description coverage.

**Actual text/choice layout overlap: [#921](https://github.com/gemrb/gemrb/issues/921)**, closed/updated 2021-04-12, nineteen comments, **outside the EE label** (`game: iwd2`, archived subviews tag). It reports missing spacing and subsequent overlap; later examples add BG1 Shandalar. The complete discussion investigates option views larger than their text, narrowing available width and portrait-dependent reflow. A proposed removal of horizontal autoresizing is [challenged because dialogue portraits change size](https://github.com/gemrb/gemrb/issues/921#issuecomment-782886761); removing it is not a justified modern fix. The final comments separate a scrollbar regression from the original layout fault and [confirm the eventual correction](https://github.com/gemrb/gemrb/issues/921#issuecomment-817983131).

The issue event history links three inspected corrections: [7604348](https://github.com/gemrb/gemrb/commit/760434821852c0a71224690f02cbc3f1e6470c07) updates the option frame after text-frame changes; [9e0ee7a](https://github.com/gemrb/gemrb/commit/9e0ee7aec1acf5625efa1fb1db3791978641bd18) aligns numbered prefixes; [62e1537](https://github.com/gemrb/gemrb/commit/62e15373cc818513017eb997f2f52e00b13357c4) accounts for changing width when scrollbars appear or IWD2 changes dialogue size. The inspected local `SpanSelector::SizeChanged` already recalculates child frames from available width, and retains horizontal autoresizing. Blindly replaying the proposed workaround would discard this history.

Our [Window audit](../testing/phase1-window-render-lab-audit.md) instead measured removed-choice pixels surviving in a retained render target, including repeated alpha accumulation; clipped clearing changed those pixels while semantic state stayed fixed. Our [TextArea reentrancy correction](../testing/phase1-textarea-native-correction-audit.md) instead concerns callbacks replacing options during public selection. Neither mechanism appears in #921's recorded investigation. Treat layout overlap, stale backing pixels and callback/index lifetime as **three separate defect families**. A shared screenshot symptom is insufficient to close/reopen upstream issues or transplant code.

**Input/modal overlap: [#848](https://github.com/gemrb/gemrb/issues/848)** remains open, last updated 2021-06-19, five comments. It discusses blocking events only below modal windows and underlying gameplay cursor/tooltips. The related [#840](https://github.com/gemrb/gemrb/issues/840), closed 2020-06-27 with six comments, explicitly moves its underlying problem into #848. The [last #848 comment](https://github.com/gemrb/gemrb/issues/848#issuecomment-864455331) says stacked modals exist but adequacy is uncertain; inspected [e3c4460](https://github.com/gemrb/gemrb/commit/e3c4460991bbb17abadd4f7673681854ae691667) indeed adds stacked-modal handling. Open status does not mean that implementation is wholly absent. Our opaque hotkey backdrop and clean dialogue repaint do not prove physical mouse hit testing, hover isolation or all stacked-modal behavior. Those require actual ordinary input/close/escape tests in declared contexts.
